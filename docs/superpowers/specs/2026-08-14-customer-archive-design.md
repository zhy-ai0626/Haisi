# 海丝企业服务中心客户管理系统设计规格

## 1. 文档信息

- 设计日期：2026-08-14
- 系统名称：海丝企业服务中心客户管理系统
- 第一版使用对象：海丝企业服务中心内部人员
- 第一版账号安排：首批账号全部为管理员，同时预置普通员工权限
- 基础平台：NocoBase Community Edition 2.1.39
- 主要技术栈：TypeScript、React、Ant Design、Node.js、Koa、PostgreSQL、Docker Compose
- 品牌资产：项目根目录 `logo01.jpg`

## 2. 目标

第一版提供一套可在电脑和手机浏览器中使用的内部客户健康档案系统。系统支持客户基本信息、来源与介绍人、授权确认、历次健康状态、体检报告附件以及内部权限管理。

系统以 NocoBase 社区版为底座，复用其账号、权限、表单、筛选、附件、Excel 导入导出和响应式布局。业务扩展放入独立的 `customer-archive` TypeScript 插件，不修改 NocoBase 核心源码。

## 3. 第一版范围

### 3.1 包含

- 内部账号登录，关闭公开注册
- 管理员和普通员工两级权限
- 客户基本档案
- 来源类型和客户标签管理
- 已有客户介绍与手工介绍人姓名
- 建档时授权确认及后台审计
- 一个客户对应多条历史健康记录
- PDF 和图片体检报告附件
- 电脑端和手机浏览器查询、录入与编辑
- 客户基本资料 Excel 导入和导出
- 客户归档和恢复
- 本地基础备份
- 可选的腾讯 COS 或华为 OBS 异地备份开关
- 升级前备份策略和风险确认
- 为未来微信端保留服务层与身份映射扩展点

### 3.2 不包含

- 方案管理
- 回访管理
- 消费和订单管理
- 经营报表和数据大屏
- 面向客户的公开网页或微信小程序
- 体检报告 OCR、内容抽取或医学判断
- 手写签名、短信验证码或人脸认证
- 自动升级
- 修改或深度定制 NocoBase 核心源码
- 将系统作为公开低代码、零代码或 AI 平台提供给第三方

## 4. 设计原则

1. 核心不修改，业务扩展独立。
2. 业务代码、部署配置和数据由项目方掌控。
3. 使用开放的 PostgreSQL 数据和普通附件文件，提供可验证的导出与恢复路径。
4. 固定 NocoBase、Docker 镜像和依赖版本，不使用浮动的 `latest` 标签。
5. 第一版优先使用 NocoBase 稳定的内置页面，不把仍在演进的 `client-v2` 作为复杂生产界面的唯一依赖。
6. 不引入必须续费才能保持第一版运行的商业插件。
7. 保留 NocoBase 许可证要求的名称、链接、版权、许可证和代码声明；允许替换的位置使用项目 Logo。
8. 只采集完成客户档案服务所需的信息，不采集身份证号或微信号。
9. 健康信息和附件按敏感数据处理，执行最小权限、审计、HTTPS 和备份保护。

## 5. 总体架构

### 5.1 运行组件

- NocoBase 2.1.39：账号、权限、页面、表单、筛选、附件、导入导出和插件宿主
- `customer-archive` 插件：业务数据模型、客户编号、授权事务、权限条件、备份设置、备份任务和未来接口边界
- PostgreSQL 16：业务数据、配置和审计记录
- Docker Compose：本地开发、验收和正式环境编排
- Nginx：正式环境反向代理、HTTPS 和上传限制
- 持久化附件目录：本地或服务器磁盘
- 可选对象存储：腾讯 COS 或华为 OBS，仅在管理员开启异地备份时使用

### 5.2 环境安排

- 开发与首次验收：当前电脑上的 Docker Compose 环境
- 正式部署：腾讯云或华为云 Linux 服务器
- 正式环境必须配置域名和 HTTPS 后才允许录入真实客户数据
- 开发、测试和正式环境分别使用独立数据库、附件目录和密钥

### 5.3 代码与数据控制边界

- 项目自有：`customer-archive` 插件、Docker Compose、Nginx 配置、备份脚本、测试和项目文档
- 第三方开源：NocoBase 核心及 React、Ant Design、Koa、PostgreSQL 等依赖，遵守各自许可证
- 项目数据：PostgreSQL 业务数据、附件、备份和导出文件
- 页面与权限配置虽然部分保存在数据库中，但必须纳入数据库备份与恢复测试

## 6. 数据模型

### 6.1 客户 `customers`

| 字段 | 类型与规则 |
|---|---|
| `id` | NocoBase 主键 |
| `customerNo` | 唯一字符串，格式 `HS-YYYYMM-######`，服务端生成 |
| `name` | 字符串，必填 |
| `gender` | 枚举：男、女、未说明，可空 |
| `birthDate` | 日期，可空 |
| `mobile` | 字符串，可空、可重复，不进行重复提示 |
| `region` | 字符串，可空 |
| `address` | 多行文本，可空 |
| `sourceType` | 多对一关联 `source_types`，可空 |
| `referrerCustomer` | 多对一自关联 `customers`，可空 |
| `referrerName` | 字符串，可空，用于介绍人尚未建档的情况 |
| `tags` | 多对多关联 `customer_tags` |
| `owner` | 多对一关联内部用户，必填，默认当前用户 |
| `status` | 枚举：正常、已归档，默认正常 |
| `establishedAt` | 日期时间，默认建档时间 |
| `remarks` | 多行文本，可空 |
| 系统字段 | 创建人、修改人、创建时间、修改时间 |

年龄不作为持久化字段，根据 `birthDate` 和当前日期显示。手机号不是身份标识；唯一身份由 `customerNo` 承担。一家人可以使用同一个手机号。

### 6.2 健康记录 `health_records`

| 字段 | 类型与规则 |
|---|---|
| `id` | NocoBase 主键 |
| `customer` | 多对一关联 `customers`，必填 |
| `recordedAt` | 日期，必填 |
| `heightCm` | 小数，可空，允许范围 30–250 |
| `weightKg` | 小数，可空，允许范围 1–500 |
| `systolic` | 整数，可空，允许范围 40–300 |
| `diastolic` | 整数，可空，允许范围 20–200 |
| `heartRate` | 整数，可空，允许范围 20–300 |
| `healthSummary` | 多行文本，可空 |
| `medicalHistory` | 多行文本，可空 |
| `allergies` | 多行文本，可空 |
| `medications` | 多行文本，可空 |
| `notes` | 多行文本，可空 |
| `attachments` | 多附件字段，可空 |
| 系统字段 | 创建人、修改人、创建时间、修改时间 |

一个客户可以拥有任意多条健康记录。客户基本资料的修改不得覆盖健康记录。健康记录默认按 `recordedAt` 降序显示。

附件仅允许 PDF、JPG、JPEG 和 PNG；单个附件上限为 30 MB。

### 6.3 来源类型 `source_types`

| 字段 | 类型与规则 |
|---|---|
| `code` | 唯一字符串 |
| `name` | 唯一字符串，必填 |
| `enabled` | 布尔值，默认开启 |
| `sortOrder` | 整数 |

初始值依次为：自然到店、老客户介绍、员工介绍、微信、活动、其他。管理员可以新增、停用和排序。停用不影响历史数据，但新建客户时不能选择已停用项。

### 6.4 客户标签 `customer_tags`

| 字段 | 类型与规则 |
|---|---|
| `name` | 唯一字符串，必填 |
| `color` | 颜色值，可空 |
| `enabled` | 布尔值，默认开启 |
| `sortOrder` | 整数 |

管理员维护标签，客户可选择多个标签。停用标签保留历史关联，但不能用于新增关联。

### 6.5 授权模板 `consent_templates`

| 字段 | 类型与规则 |
|---|---|
| `title` | 字符串，必填 |
| `version` | 唯一字符串，必填 |
| `content` | 长文本，必填 |
| `isCurrent` | 布尔值，同一时间只能有一个当前模板 |
| `publishedAt` | 日期时间，必填 |
| 系统字段 | 创建人、修改人、创建时间、修改时间 |

新版本发布后，旧版本不可再用于新授权，但历史授权保留原版本和正文快照。

### 6.6 授权确认 `consent_confirmations`

| 字段 | 类型与规则 |
|---|---|
| `customer` | 多对一关联 `customers`，必填 |
| `template` | 多对一关联 `consent_templates`，必填 |
| `templateVersion` | 字符串快照，必填 |
| `contentSnapshot` | 长文本快照，必填 |
| `confirmedAt` | 日期时间，必填 |
| `confirmedBy` | 多对一关联内部用户，必填 |
| `revokedAt` | 日期时间，可空 |
| `revokedBy` | 多对一关联内部用户，可空 |
| `revocationReason` | 多行文本，可空 |

授权确认只允许创建和撤回，不允许直接编辑或覆盖。授权状态不显示在客户基本信息区或客户列表，只在管理员审计页面查询。

## 7. 初始授权模板

标题为《客户信息与健康资料授权告知》，初始版本为 `1.0`，正文如下：

> 海丝企业服务中心为建立和维护客户档案、记录客户历次健康状态、保存体检报告及提供相关客户服务，需要收集并使用客户的姓名、性别、出生日期、联系方式、地址、健康状态、病史、过敏史、用药情况、体检报告等信息。
>
> 上述信息仅用于客户档案管理和相关服务，由获得授权的内部工作人员在必要范围内查询和使用。未经客户同意，不向无关第三方出售、公开或用于与上述目的无关的事项；法律法规另有规定的除外。
>
> 客户有权申请查询、更正或删除相关信息，也可以撤回授权。撤回授权不影响此前基于授权进行的信息处理。

员工确认项固定为：

> 我已向客户完整说明上述内容，并已获得客户对收集、存储和使用其个人信息及健康资料的明确同意。

建档人只有勾选该确认项才能提交。系统不采集手写签名。该模板是产品初始文本，不替代正式法律意见；录入真实客户数据前应完成合规复核。

## 8. 业务流程

### 8.1 新建客户

1. 登录用户打开新建客户表单。
2. 填写基本信息、来源、介绍人、标签和负责人。
3. 页面展示当前有效授权模板全文。
4. 用户勾选员工确认项。
5. 服务端校验必填项、权限和当前模板。
6. 服务端在同一数据库事务中生成客户编号、创建客户和创建授权确认。
7. 任一步失败时回滚全部数据并返回可理解的错误信息。
8. 成功后打开客户详情页。

### 8.2 新增健康记录

1. 用户从客户详情进入健康记录页签。
2. 系统先校验用户对该客户的访问权限。
3. 用户填写日期、生命体征和文字信息。
4. 用户上传零个或多个附件。
5. 系统校验格式、大小和数值范围后保存。
6. 新记录按日期插入历史列表，不修改既有记录。

附件上传失败时显示具体文件和原因，不创建无效附件关联。已成功上传的文件必须与健康记录保持一致；如果整条健康记录提交失败，未关联的临时文件由清理任务回收。

### 8.3 归档与删除

- 日常界面提供归档和恢复，不提供直接删除按钮。
- 归档客户仍保留健康记录、附件和授权历史。
- 真正删除只允许管理员在专门入口执行，并要求二次确认。
- 删除前明确列出将受影响的健康记录和附件数量。
- 法律或审计要求必须保留的记录不得因普通删除操作而悄然消失。

### 8.4 授权撤回

- 管理员在授权审计页执行撤回，填写原因。
- 系统记录撤回时间和操作人，不修改原授权快照。
- 撤回后继续新增健康信息前必须重新获得授权并创建新确认记录。
- 撤回不自动删除既有数据；删除请求由管理员按适用规则另行处理。

### 8.5 Excel 导入与导出

- 第一版导入和导出的对象是客户基本资料，不在 Excel 中嵌入附件文件。
- 导入仅允许管理员执行。
- 模板允许手机号为空或重复。
- 每行必须包含 `授权已确认=是`，导入管理员记为确认操作人。
- 每行独立执行事务；错误行不产生客户或授权记录。
- 导入结果列出成功数量、失败数量、具体行号和原因。
- 导出遵循当前用户的数据权限；管理员可以导出全部客户。

## 9. 页面与移动端设计

### 9.1 登录页

- 标题：海丝企业服务中心客户管理系统
- Logo：项目根目录 `logo01.jpg`
- 关闭公开注册和找回账号之外的公开入口
- 保留许可证要求的平台信息

### 9.2 客户管理页

列表字段：客户编号、姓名、性别、年龄、手机号、来源、介绍人、标签、负责人、状态、建档日期。

筛选条件：姓名、客户编号、手机号、来源、标签、负责人、状态。

默认只显示正常客户，管理员可切换查看已归档客户。页面提供新建、导入、导出和归档操作。

### 9.3 客户详情页

使用三个页签：

1. 基本信息：查看和编辑客户资料。
2. 健康记录：按日期倒序查看、新增和编辑。
3. 操作记录：管理员查看建档、修改、归档和授权事件。

### 9.4 管理设置

仅管理员可见：来源类型、客户标签、授权模板、内部账号、授权审计、备份管理。

### 9.5 手机端

- 客户列表使用紧凑卡片布局。
- 顶部保留姓名、手机号和客户编号搜索。
- 客户详情使用纵向页签或折叠区块。
- 表单字段单列展示，主要操作按钮保持可见。
- 附件可从手机相册、文件选择器或摄像头添加。
- 第一版使用 NocoBase 响应式页面，不开发独立微信界面。

## 10. 权限设计

### 10.1 管理员

- 查看、创建和编辑全部客户及健康记录
- 归档和恢复客户
- 执行受保护的删除操作
- 导入和导出全部客户
- 管理来源、标签、授权模板、账号和备份设置
- 查看完整授权和操作审计

### 10.2 普通员工

- 新建客户和健康记录
- 只能查看和编辑 `owner` 为本人或创建人为本人的客户
- 只能访问上述客户的健康记录和附件
- 可以在建档时创建授权确认
- 不能归档、恢复或删除客户
- 不能管理来源、标签、模板、账号或备份
- 不能查看完整审计页面

第一批账号全部分配管理员角色。普通员工角色必须在第一版验收时使用测试账号验证，但暂不分配给正式人员。

## 11. 备份与升级

### 11.1 本地基础备份

- 默认开启，不依赖额外付费服务。
- 同时备份 PostgreSQL 和附件目录。
- 数据库文件与附件快照使用同一时间标识。
- 默认保留最近 7 份日备份和 4 份周备份。
- 管理员可以关闭；关闭后管理页持续显示“当前无可用自动备份”的高风险提示。
- 关闭备份、删除备份和跳过升级前快照均写入审计记录。

### 11.2 云端异地备份

管理页提供 `启用云端异地备份` 开关，默认关闭。关闭状态不产生腾讯 COS 或华为 OBS 的存储费用。

开启后管理员选择腾讯 COS 或华为 OBS，并配置：

- 存储桶和区域
- 访问凭证引用
- 执行时间
- 保留数量
- 服务端加密选项

管理员可以在备份设置页录入对象存储凭证。服务端使用由环境变量提供的主加密密钥加密保存凭证；查询接口只返回掩码，不返回明文。主加密密钥和明文凭证不写入 Git、普通日志或页面响应。界面显示最近执行时间、结果、占用空间和失败原因。

关闭开关后停止上传新备份，但不自动删除云端已有备份。删除已有云备份必须由管理员单独选择并二次确认。

### 11.3 升级策略

- 系统不自动升级，版本变更由管理员主动执行。
- `升级前自动备份` 默认开启，至少创建本地完整快照。
- 管理员可以关闭并二次确认跳过，系统记录操作人、时间、版本和风险确认。
- 升级前在副本环境验证数据库迁移、插件、权限、页面、导入导出和附件。
- 升级失败时使用升级前快照回滚应用版本、数据库和附件。

### 11.4 恢复验证

- 每季度执行一次实际恢复演练。
- 恢复验收包括客户、健康记录、授权记录、页面权限和附件一致性。
- 只检查备份文件存在不算恢复验证通过。

## 12. 错误、安全与审计

- 未勾选授权时禁止建档，并在字段旁显示明确提示。
- 手机号重复不检查、不提示、不阻止保存。
- 数值字段拒绝文字、负数和超出已定义范围的值。
- 无权访问的资源返回拒绝访问，不向用户泄露记录内容。
- 密码、数据库连接和对象存储密钥使用环境变量或受保护配置。
- 正式环境强制 HTTPS。
- 数据库和备份账号使用最小权限。
- 普通应用日志不输出客户完整健康资料、授权正文或附件内容。
- 审计至少记录操作人、时间、动作、集合、记录编号和结果。
- 客户建档与授权创建必须是原子事务。
- 来源和标签停用后保留历史显示，但不能用于新增选择。
- 系统时间统一保存为 UTC，页面按 Asia/Shanghai 显示。

## 13. 未来微信端扩展边界

第一版不开放公网客户接口，但插件服务层必须将下列能力封装为独立业务方法：

- 查询允许访问的客户
- 创建和更新客户
- 创建授权确认
- 新增健康记录
- 上传和关联附件

未来微信端只能通过带身份认证、权限判断、速率限制和审计的 API 调用这些方法，不允许直接访问数据库。微信用户与内部用户或客户身份的映射在后续单独设计。

## 14. 测试策略

### 14.1 单元测试

- 客户编号格式和唯一性
- 年龄计算边界
- 普通员工数据权限条件
- 授权模板快照
- 授权撤回规则
- 本地与云备份开关状态
- 附件类型和大小校验
- 生命体征范围校验

### 14.2 集成测试

- 成功建档同时生成授权记录
- 未勾选授权时客户和授权均不创建
- 事务中任一步失败时完整回滚
- 手机号为空、重复和家庭共用均可保存
- 同一客户创建多条健康记录
- 普通员工不能访问其他客户的健康记录和附件
- 停用来源或标签不破坏历史关联
- Excel 正确行导入、错误行回滚和错误报告
- 备份任务同时生成数据库和附件快照
- 关闭云备份后不再产生上传任务且不删除历史备份

### 14.3 端到端测试

- 管理员登录、新建客户、勾选授权、添加健康记录和上传体检报告
- 客户查询、筛选、编辑、归档和恢复
- 授权模板发布新版本后历史快照保持不变
- 桌面浏览器完整流程
- 常见手机宽度下的列表、详情、表单和附件上传
- 使用测试普通员工账号验证数据隔离
- 管理员开启、关闭和查看备份状态

### 14.4 恢复测试

从一套匹配时间标识的数据库与附件备份恢复新环境，验证记录数量、关联关系、权限、授权正文快照和附件可读性。

## 15. 第一版验收标准

1. 管理员可以登录，公开注册已关闭。
2. 系统名称与项目 Logo 正确显示，同时保留必要的平台信息。
3. 客户可以新建、查询、筛选、编辑、归档和恢复。
4. 未勾选授权无法建档；成功建档后存在不可直接编辑的授权记录。
5. 手机号为空、重复或一家多人共用时都能正常保存。
6. 一个客户可以拥有多条互不覆盖的健康记录。
7. 可以上传并查看本机体检报告样例，样例不得提交到代码仓库。
8. 来源、介绍人、标签和负责人按设计工作。
9. Excel 导入导出正确处理中文、空手机号和重复手机号。
10. 测试普通员工只能访问本人负责或录入的客户。
11. 电脑端和手机浏览器完成主要流程。
12. 本地备份开关、云备份开关、状态提示和审计符合设计。
13. 从备份恢复后，客户、健康记录、授权记录、页面权限和附件一致。
14. 自动测试、集成测试和端到端验收全部通过。
